# Deploying
In lesson #4, you learned how to create a Dockerfile, how to build your image, and how to deploy a container using a very basic repository. 

As your projects get more complicated, deplying the container also gets more complicated. For example, if you are deploying an API, you may need to let the container know what port to expose the API to. Or if you are deploying a database, you need to let the container know what the database name should be, what the username and password are, or where to actually put the database in the file system.

Lets break down the arguments in a docker run command further:
```cmd
docker run -d --name my-first-container my-python-app
```

| Parameter | Usage |
|---|---|
| -d | Run the container as 'detached'. This means you can run it in the background so you can still use your terminal.|
| --name | Gives your container a readable name. Without it, docker creates one for you like "nostalgic_feynman" or "excitable_toaster" |
| -rm | Delete the container automatically when it exits. Great for one-off tasks|
| --restart unless-stopped | If the container crashes or the machine reboots, auutmatically starts the container again. Available options: no, on-failure, always, unless-stopped |
| -i | Once started, the terminal will let you type directly into the container |
| -t | Allocate a pseudo-terminal (prompt autocomplete, colors, line editing, etc) |
| -it | Combines the -i and -t parameters into one |
| -p ####:#### | Publish a specific port using HOST:CONTAINER formatting ie "Traffic hitting port 8080 on my machine goes into port 3000 in the container" |
| -P | Publish ALL ports (rarely what you wnat) |
| --network myapp-net | Attach the container to a specific Docker network so it can talk to other containers on the same network |
| --hostname db | Set the containers internal hostname |
| -v .src:/app/src | Bind mount. Connects a real folder on the host machine to a path within the container. |
| -e | Sets an environment variable inside the container |
| --env-file .env | Load a whole file of environment variables at once |
| -w /app | Sets the working directory (overrides the WORKDIR from the Dockerfile) |
| -u 1000:1000 | Run the process as a specific user or group (service account) |

# Why do you need this?
Lets say you need to spin up a postgres database. To run a container for [Postgres](https://hub.docker.com/_/postgres), you would run:
```cmd
docker run -d --name db postgres:16
```

If you were to run this though, you would get an error because the image requires you to pass in variables required to set up the database.

According to the documentation, these are all the environment variables for postgres:
| Name | Required | Usage |
| --- | --- | --- |
| POSTGRES_PASSWORD | Yes | Sets the superuser password for PostgreSQL |
| POSTGRES_USER | No | Sets the superuser name for PostgreSQL. Defaults to `postgres` if left blank |
| POSTGRES_DB | No | Define a different name for the default database |

At minimum, your run command would now look like this:
```cmd
docker run -d --name db \
-e POSTGRES_USER=SuperUser \
-e POSTGRES_PASSWORD=SuperPassword \
-e POSTGRES_DB=DatabaseName \
postgres:16
```

But now, you also want to set the restart conditions so that the container is restarted if the host machine restarts or if the container fails:
```cmd
docker run -d \ 
    --name db \
    -e POSTGRES_USER=SuperUser \
    -e POSTGRES_PASSWORD=SuperPassword \
    -e POSTGRES_DB=DatabaseName \
    --restart unless-stopped \
    postgres:16
```

And now, you also want a graphical user interface for the database like [PGAdmin](https://hub.docker.com/r/dpage/pgadmin4).
```cmd
docker run -d \
    --name pgadmin \
    -p 5050:80 \ 
    -e "PGADMIN_DEFAULT_EMAIL=user@example.com" \
    -e "PGADMIN_DEFAULT_PASSWORD=your_secure_password" \
    dpage/pgadmin4
```

This is a LOT to have to remember and doesn't make it very reusable. Its hard to memorize and if someone types a slightl different flag, their setup behaves differently than another persons. You also now have 2 containers running that cannot talk to each other and your PGAdmin instance will never be able to connect to your database.

This is where Docker Compose comes in.

# Docker Compose
A Docker Compose file is a YAML file that acts as the menu. It allows you define and run multi-container applications, set environment variables, define networks, and assign volumes all in one file.

YAML files are human readable versions of JSON files and turn  complex data structures into a clean, easy to read text format. Instead of nested brackets like JSON, it uses indentations (spaces, not tabs) to define keys and values.

JSON example:
```JSON
{
    "app_name": "MyApplication",
    "version": 1.0,
    "database": {
        "host": "localhost",
        "port": 5432
    },
    "features": ["login","dashboard","settings"]
}
```

YAML conversion:
```YAML
app_name: MyApplication
version: 1.0
database:
  host: localhost
  port: 5432
features:
  - login
  - dashboard
  - settings
```

Lets take our previous Postgres and PGAdmin example. Take a look at the docker-compose.yml file:

## So what does each section do/mean?
### Top level
`services`: Required and tells Docker what containers to start.
`volumes`: Where data lives
`networks`: How things talk to one another

### Block 1: Services
```yaml
services:  
  db:          # <- service name (you define this)  
    ...  
  pgadmin:     # <- another service name  
    ...  
```

### Block 2: Services
```yaml
  db:  
    image: postgres:16           # which image to run  
    container_name: tutorial-db  # the actual container's name  
    restart: unless-stopped      # what to do if it crashes  
    environment:                 # config passed into the container   
    ports:                       # expose a port to the host machine  
    volumes:                     # attach storage  
    healthcheck:                 # how to know it's actually ready  
    networks:                    # which networks to join  
      - backend  
```

Image vs Build
If you are building your own container and do not have a published image on hub.Docker.com, you would replace "image" with "build: ." to build the current project based on the Dockerfile.

### Block 1: Volumes
```yaml
volumes:  
  db-data:  
  pgadmin-data:  
```
This looks odd at first because the values are empty. All it means is: "Docker, please create and manage two storage areas with these names." The empty value means "use all the defaults," which is almost always what you want.

### Block 1: Networks
```yaml
networks:  
  backend:  
```
Same idea: "create a network called backend."

If you notice in the `environment` sections, no value is actually passed in. Dockercompose files are intended to be committed to git, so you never want to hardcode your environment variables in these files. By using `${}`, you are telling Docker to use the .env file and extract the corresponding value (similar to os.getenv()). The value after defines a default value in case the user does not provide an override

```yaml
POSTGRES_USER: ${POSTGRES_USER:-appuser}
```
In the above, `POSTGRES_USER` is expected to be in the .env file. If its not or is left blank, it will default the value to `appuser`.

Based on this specific Docker Compose file, your .env file would look like this:
```
POSTGRES_USER=appuser  
POSTGRES_PASSWORD=supersecret  
POSTGRES_DB=myapp  
PGADMIN_EMAIL=admin@example.com  
PGADMIN_PASSWORD=admin123  
```

Since some compose file will have MANY variables, its always good to include a `.env.example` file, which contains a list of the keys required. Since there are no secrets being exposed here, this CAN and SHOULD be committed to Github. For this tutorial, the .env file IS committed since it does not contain any real data, but in production environments, the .env would NEVER be committed.

# Running Docker Compose
Now that you have a docker-compose file.yml file, you can instead run the following to start both containers at once.
```cmd
docker compose up -d
```

Since you've now established them on the same network, the two containers can talk to each other. In PGAdmin, you can run queries and see the tables for the database. To connect to your database, your 'host' would be `db:5432`. `db` represents the service name and `5432` is the port that that service is running on. You don't need to worry about or configure IP addresses or anything like that. Both the database and PGAdmin are ONLY accessible from within the container.
