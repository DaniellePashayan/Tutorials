# Docker Fundamentals

1. DockerFile ("The Recipe")
This is a text file that contains a list of steps for creating your application environment. For example, it tells the container: "Start with Ubuntu, install this version of Python, install that version of UV, copy these scripts into this directory, and then run this command".

2. Docker Image ("Cake Mix")
A docker image is the output of running the DockerFile and is a 'ready to be distributed' snapshot. It contains the exact OS, libraries, and code from a point in time. You are not limited to just deploying containers that you create though. Similar to Github, [Docker Hub](https://hub.docker.com/) contains images for open source containers. For example:
    - database engines like Postgres
    - a self hostable word press server
    - a dashboarding platform like Grafana
    - a spotify analytics platfom

3. Docker Container ("The Cake")
The living, breathing environment that is the result of starting the image. It is the isolated box running on the host that executes the software. It can be started, stopped, restarted, or deleted at any time and in seconds. Containers are temporary. Once a container is stopped or deleted, any data generated inside of it is also deleted (see "Volumes" for further detail)

4. Docker Compose ("The Bakery")
Compiles multiple containers into a "stack" that can be deployed at once. You can have one container running the API, another container running the website, and another container running the database. 

5. Volumes
Volumes map to the host's file system and allow for the persistence of data outside of the container. It is a one way track where the container can access ONLY its mapped volume and nothing more. However, the host can see the data from all container volumes.

6. Networks
Networks enable isolated containers to a) talk to one another b) talk to the host machine c) talk to external networks (other websites). 

# Real Life Utility
- You create a python script that calls an API and writes the data to a database. The script is deployed in its own container
- For development, you set up a separate database container with a development database
- The production database is in its own container
- You use pgAdmin as the GUI for the databases
- You use Grafana to show analytics/dashboards on the database contents
- You use UpTimeKuma to monitor the health of both your containers and the API you are calling

You now have 6 containers all related to the same project, so you create a stack for them using docker compose so all the pieces are linked. The production database has its own volume, meaning the data persists even if the container is stopped/deleted, but the development database does not, so each time you restart that container, the data inside the database resets. They all share a network, meaning the 6 of them can talk to each other.
