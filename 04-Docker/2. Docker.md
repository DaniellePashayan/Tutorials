# Docker
So what does understanding virtualization have to do with software development?

I'm sure you've heard the joke of "well it works on my machine" when someone else is trying to run your code. Docker helps to solve this by packaging an application and all of its dependencies into a standard, isolated container.

With Python, a virtual environment sounds like it would solve all of the above problems. While virtual envuronments help to ensure reproducability across different devices, it does not eliminate issues entirely. A virtual environment only isolates the Python packages and scripts at the application level, whereas a Docker container isolates the entire operating system.

## So what exactly is Docker?
Docker is a software platform that simplifies the process of building, running, managing, and deploying applications by packing them into individual, isolate environments. These isolated environments are called "container". 

Think of it like a shipping container. Anything you put inside the shipping container is only accessible from within that container, but you can then load a bunch of containers onto a cargo ship or truck for transport. 

It packages the application code along side every single dependency, library, and configuration it needs to run and eliminates all environmental discrepancies.

## Docker Use Case Examples
1. Environments
- You can have different environments of code and databases, such as Production, Development, or Staging 
- Real world example: EPIC has MANY different environments, all with their own data. TST, STG, PJX, and PROD all have different data within their databases, but their structure and setup is the same. This allows developers to write code in Development environments and they know that if it works in the dev environment, it will work in PROD.

2. Scaling
- You have a website or service and the traffic increases significantly. You can deploy more containers to handle the workload and be assured that each container will have the exact same setup. If you were to upgrade something about the source code, it can then also be automatically deployed to ALL the containers at once.
- Real world example: Right now, Sutherland uses individual virtual machines to manage their bots. We've had many issues in the past where one of the VMs has a different configuration that another and the bot breaks. In an ideal world, the bot code would be Dockerized, so if they needed to deploy a new bot on the fly, they could spin up a new container and ensure that a) the container has EVERYTHING it needs to run b) the configuation between all the different containers is exactly the same 

3. Security and Isolation 
- You need multiple databases to store information for different clients, but the host OS only allows for 1 installation of the database at the OS level. While you could add different tables (one for each client), there is a risk that client A could access client B's data.
- Real world example: You have multiple clients, each of which requires a database. Instead of installing a database management tool (MS SQL, Postgres, etc) on the host machine (server), you can create one container for each client that contains your python code AND the database. Container A will never be able to access Container B's files, which includes the database.
